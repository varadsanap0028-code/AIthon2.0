# SARATHI Student Portal: Skill Assessment Reliability, Secure Exam Mode & Analytics
## Product Requirements Document (PRD)

| Field | Value |
|---|---|
| Product | SARATHI, Student Portal, Skill Assessment |
| Document type | PRD |
| Version | 1.0 |
| Date | 19 Oct 2026 |
| Status | Draft for implementation |
| Scope | Student Skill Assessment + directly related backend, persistence, history, report, statistical chat. **Recruiter and Employer portals are out of scope.** |

---

## 1. Summary

Students complete a skill assessment and see a score and analysis, but the result **disappears after refresh or when returning to the Skill Assessment page**, sometimes dropping the student back to Practice/Secure mode selection. Earlier fixes passed tests and builds but did not fix the running app.

This PRD defines the work to:

1. Find and prove the root cause of the persistence failure, then fix it durably.
2. Replace the confusing Practice/Secure choice with one unified start flow, while keeping two real assessment policies internally.
3. Make Practice and Secure behave genuinely differently.
4. Give every new attempt a fresh, fair, auditable question set.
5. Show one consolidated, data-honest statistical and diagrammatic report.
6. Preserve full attempt history and retake behavior.
7. Keep the statistical chat consistent with the saved report.
8. Apply sound security, privacy, and integrity practices.

> **Reported stack (verify before relying on it):** React, TypeScript, Vite, Node.js, Express, SQLite.
> **Reported components (starting points only):** `AssessmentV2Shell.tsx`, `ResultsReport.tsx`, `CompletedAssessmentSummary.tsx`, `assessmentV2Routes.js`, `aiChatService.js`.

---

## 2. Problem Statement

### 2.1 Critical bug (P0)
After completing an assessment, refreshing or revisiting the page loses the score and analysis. The app may show mode selection instead of the completed report. Automated tests and builds passing did not reflect real behavior, which suggests the tests do not exercise the real submit, refresh, restore path.

### 2.2 Secondary problems
- Two upfront modes (Practice/Secure) confuse students and may not differ meaningfully.
- Questions may be hardcoded or repeated across attempts.
- A simplified summary and a detailed report may duplicate information.
- History, retake, and chat may rely on different or stale data sources.
- Integrity and camera claims risk overstating what is actually implemented.

---

## 3. Goals and Non-Goals

### Goals
- G1. A completed attempt and its authoritative result are always persisted server-side and restorable.
- G2. One start flow; two internally distinct, honestly labeled policies.
- G3. New attempt = new attempt ID = fresh question set; in-progress attempts are stable across refresh.
- G4. One detailed report is the primary view for new and historical attempts.
- G5. Zero, missing, and unexecuted are always distinguishable.
- G6. Integrity signals are advisory, transparent, privacy-minimal, and never auto-punitive on ambiguous evidence.
- G7. Verified end to end in a real browser, not only unit tests.

### Non-Goals
- Changes to Recruiter or Employer portals.
- Guaranteeing prevention of all cheating (browser limits apply).
- Automated misconduct verdicts from gaze or camera signals.
- Storing or transmitting camera footage.
- Guaranteeing every question is globally unique when the bank cannot support it.

## 5. Phase 0: Investigation (Mandatory Before Any Fix)

The root cause must be **reproduced and proven** before another fix is applied. Trace the full lifecycle:

`Auth → Session → Questions/Answers → Submit → Server scoring → DB persistence → Result API → Frontend restore → Detailed report`

### Checklist
| # | Question to answer with evidence |
|---|---|
| 1 | Does the backend commit the attempt and score to the DB **before** returning success? |
| 2 | Does the frontend re-fetch the **same attempt ID** after refresh? Where is the ID stored (URL, storage, server)? |
| 3 | Does auth initialization, token handling, or student identity change on refresh and break retrieval? |
| 4 | Are frontend and backend using the **same database file and environment**? |
| 5 | Do API response shapes, SQL joins, domain filters, or session identifiers omit saved results? |
| 6 | Does the report depend on transient React state rather than persisted server data? |
| 7 | Is an API error treated as "no assessment" or a legitimate zero score? |
| 8 | Do completion and history retrieval use **different data sources**? |

### Deliverable
A written root-cause analysis with reproduction steps, logs/DB queries/network traces, and an explanation of why earlier fixes and tests failed to catch it.

## 6. Functional Requirements

### FR-1. Durable results (P0)
1. Persist completed attempt and server-computed result in one transaction.
2. Return success only after commit; UI shows completion only after confirmation.
3. On refresh, fetch the saved attempt and render the existing report.
4. Restore correct results after navigation, logout/login (same student).
5. Preserve all prior attempts when a new one starts.
6. Isolate by authenticated student, attempt, and career track/domain.
7. Provide explicit loading, retry, auth-expired, not-found, and server-error states.
8. Never substitute a missing result with a zero score or a new session.
9. Idempotent submission: retries and double-clicks must not create duplicate completed attempts.
10. Regression tests reproduce the original failure and prove the fix.

**Attempt state machine:** `created → in_progress → submitting → completed` (plus `abandoned` / `expired` if applicable). Completed attempts are immutable.

### FR-2. Unified start flow
- One "Start Assessment" entry explaining: what is assessed, structure (quiz + practical), duration, how results are saved, and what each policy means.
- Policy is determined by a clear, understandable choice inside the unified flow (for example, an explicit "Practice" vs "Secure assessment" selection with plain-language consequences) or by assessment context. The final design must be justified in the implementation report.
- Existing records keep their original mode/policy label. Do not rewrite history.
- Do not delete the mode distinction without analyzing its impact on grading, integrity, saved attempts, and legacy data.

### FR-3. Practice policy
| Aspect | Behavior |
|---|---|
| Purpose | Learning and skill improvement |
| Copy/paste | Allowed |
| Workbench | Code edit and run supported |
| Feedback | Hints, explanations, learning guidance per assessment design |
| Camera | Not required |
| Result label | "Practice result" (not proctored or verified) |
| Persistence | Saved; report restorable after refresh |
| Retake | New attempt with fresh question set |

### FR-4. Secure policy

**4.1 Copy/paste restrictions** (within assessment answer fields and workbench only)
- Block copy, cut, paste via keyboard (Ctrl/Cmd + C/V/X), context menu, and drag/drop where applicable.
- Apply consistently to answer inputs and the code editor (verify how the editor component handles clipboard events).
- Do not interfere with browser chrome or unrelated app areas.
- Explain restrictions before start. State clearly that browser-level restrictions **cannot** stop copying from external apps or devices.

**4.2 Camera readiness**
- Explain why camera is requested and how it is used (before the permission prompt).
- Request browser permission; verify device availability; show live preview and readiness status.
- If permission or hardware is unavailable, do **not** start the camera-dependent assessment. Offer a clear recovery path (retry, instructions, or an explicitly defined alternative).
- Gracefully handle: permission denied, device disconnected mid-session, unsupported browser, transient failure.

**4.3 Monitoring and gaze / attention**
- Use camera monitoring **only if a real, tested implementation exists**.
- If gaze/face-orientation analysis is implemented: treat as an *attention indicator*, never proof of cheating; tolerate normal glances, reading, glasses, lighting, camera position, and accessibility needs; use documented thresholds; warn visibly and log before escalating; no automatic failure from uncertain estimates; provide a review/appeal path for any consequential decision.
- If not implemented, **do not claim it exists** in UI or reports.

**4.4 Integrity event policy**

| Event | Warn student | Log for review | May affect outcome |
|---|---|---|---|
| Blocked copy/paste attempt | Yes (non-punitive notice) | Yes (count + timestamps) | No automatic effect |
| Camera permission revoked / feed lost | Yes, with recovery option | Yes | Pause or flag per policy; not auto-fail |
| Repeated attention anomalies (only if validated) | Yes | Yes | No automatic effect; human review only |
| Tab/focus change (only if in policy) | Yes | Yes | No automatic effect |

Each event stores: attempt ID, category, timestamp, minimal metadata. No footage, no unnecessary personal data. A single ambiguous event never triggers a misconduct label.

**4.5 Secure completion**
- Same authoritative grading and persistence as Practice.
- Skill score is kept separate from integrity events.
- Report labels reflect only what was **actually operational** (for example, "Secure assessment: copy/paste restricted, camera monitoring active" vs. "camera unavailable"). Never say "securely proctored" unless required controls ran.

### FR-5. Question freshness
1. Server-side selection by domain, career track, skills, and difficulty blueprint.
2. Controlled strategy (for example, seeded stratified random selection by skill and difficulty), not hardcoded lists.
3. Avoid repeating the complete previous set when the bank allows; define a documented **overlap policy** (for example, max N% overlap with the previous attempt) and a fallback when the bank is small.
4. Freeze the question set (IDs, order, option order, versions) at attempt creation; refresh never re-generates or reorders.
5. New attempt = new attempt ID + fresh set.
6. Earlier attempts retain their original questions and results.
7. Keep sets comparable in difficulty, skill coverage, and scoring.
8. Store question version, selection seed/strategy, and blueprint metadata for audit/reproduction.
9. Do not claim global uniqueness the bank cannot support.

### FR-6. Consolidated report
One detailed report (reuse `ResultsReport` if still appropriate) used for new and historical attempts. **No simplified summary followed by a duplicate detailed report.**

| Section | Content |
|---|---|
| A. Overview | Target career track, date, completion status, attempt number/ID, correctly labeled assessment type, overall demonstrated score |
| B. Knowledge & practical | Quiz score, workbench score, **configured** weights (read from app config, not hardcoded), correct answers / tasks passed, scoring formula explained, progress bars |
| C. Skill gap analytics | Chart per skill: student score vs role benchmark, difference, gap status, recommended next action; readable on small screens |
| D. Skill table | Skill, category, score, proficiency level, benchmark, gap status, next action |
| E. History | Line chart or equivalent, only when enough comparable data points exist |
| F. Action plan | Top gaps with learning actions/roadmap links using existing features |

**Statistical integrity rules**
- Use only saved results; do not invent benchmarks, proficiency levels, or trends.
- Distinguish **zero**, **missing**, and **not executed**.
- Charts, cards, and tables must agree (single data source/selector).
- Historical reports are never overwritten.

### FR-7. History and retake
- All completed attempts preserved; retake always creates a new attempt.
- Attempts are selectable and open the same detailed layout with that attempt's questions, scores, skills, date, domain.
- A track with no result never falls back to another track's result.
- "Retake Assessment" appears **once**, in the main report action area.

### FR-8. Statistical chat
- Use the correct saved attempt as context; enforce ownership.
- Statistics must match the displayed report (same source).
- No stale, hardcoded, or fabricated data; if results can't load, say so clearly.
- Complements the report; does not duplicate it.

---

## 7. Security and Privacy Requirements

- Backend verifies ownership of every session and result; never trusts client-supplied student ID or client-calculated score.
- Enforce career-track/domain isolation server-side.
- Store only data needed for scoring, persistence, and defined integrity review.
- Camera use explained; browser permission obtained; failures handled.
- No camera footage stored or transmitted unless explicitly designed and justified (default: none; local processing only).
- Define retention and access rules for integrity logs (who can read, how long kept, deletion).
- No high-impact misconduct decisions from unreliable automated signals.
- Idempotent submission to prevent duplicates from retries.

---

## 8. Data Model Guidance

Inspect the existing schema first and **extend rather than duplicate**. Likely needs (adapt to existing tables):

- `assessment_attempts`: id, student_id, domain/track, policy (practice|secure), status, started_at, completed_at, attempt_number, question_set_version, selection_seed, blueprint, idempotency key, policy-capabilities-actually-active snapshot.
- `attempt_questions`: attempt_id, question_id, question_version, order, option order, difficulty, skill.
- `attempt_answers`: attempt_id, question_id, answer, saved_at.
- `attempt_results`: attempt_id, quiz_score, practical_score, overall, weights used, per-skill scores, benchmark snapshot, formula/version.
- `integrity_events`: id, attempt_id, category, timestamp, minimal metadata.
- Migration must preserve legacy records and map legacy mode values.

## 9. API Guidance

Prefer extending existing routes. Capabilities required:

| Capability | Notes |
|---|---|
| Create attempt | Server picks question set; returns attempt ID |
| Get attempt (in-progress) | Returns frozen questions + saved answers |
| Save answer / progress | Authenticated, owned |
| Submit attempt | Idempotent; scoring server-side; transactional |
| Get result by attempt ID | Owned; distinguishes 401 / 403 / 404 / 5xx |
| List attempts | By student, filterable by track |
| Log integrity event | Owned attempt only |
| Chat context | Same result source as report |

## 10. Non-Functional Requirements

- Responsive, consistent with SARATHI's existing design.
- Accessible (keyboard, screen-reader labels, color-independent status).
- Clear error and loading states; no silent failures.
- Observability: server logs for submit, persist, and fetch outcomes.
- Backward compatible with existing data.

---

## 11. Acceptance Criteria

1. Complete → refresh → same attempt, same score, same detailed report (verified in a real browser).
2. Navigate away/back and logout/login both restore the correct report.
3. Second attempt completes; first remains accessible and unchanged.
4. Auth expiry, network failure, missing record, and save failure each show distinct, correct UI; none shows a zero score.
5. Double submit yields exactly one completed attempt.
6. Two deliberate attempts differ per the documented overlap policy; refresh keeps questions and answers unchanged.
7. Practice allows paste/run/hints and is labeled practice; Secure blocks clipboard in scoped fields and states limitations.
8. Camera denial/disconnect/unsupported handled; no camera-dependent start without readiness.
9. Gaze/camera anomalies never auto-fail; reports show only implemented, validated signals.
10. Report shows one view only; charts, tables, cards agree; weights come from config.
11. Cross-track and cross-student access is rejected.
12. Chat statistics match the report.

---

## 12. Test Plan

**Persistence:** save verified in DB; refresh; navigate; logout/login; second attempt; simulated auth expiry, network failure, missing record, save failure; zero-vs-missing.
**Question selection:** two attempts differ per policy; in-progress refresh stable; track and blueprint alignment.
**Modes:** unified entry clarity; practice behavior; secure clipboard restrictions; camera readiness/denial/disconnect/unsupported; no unjustified failing result; only validated signals in reports.
**Report:** direct open after submit; restore after refresh/login; data consistency; history isolation; no unrelated domain.
**Levels:** frontend unit, backend unit, API integration, production build, **end-to-end browser tests (Playwright or equivalent) covering the original refresh failure**.
If browser automation cannot run, state exactly what was not verified; never claim manual testing that did not occur.

## 14. Risks and Open Questions

| Risk / Question | Mitigation |
|---|---|
| Root cause may be environmental (wrong DB path, token init race) rather than code logic | Prove with evidence in Phase 0 |
| Question bank too small for freshness | Documented overlap policy and fallback |
| Gaze estimation unreliable | Ship only if validated; otherwise omit and don't claim it |
| Code editor (e.g., Monaco/CodeMirror) clipboard handling differs | Test per editor component |
| Legacy attempts lack metadata | Show "not recorded" rather than inventing values |
| Who reviews integrity events, and for how long are they retained? | Product decision required |
| Policy chosen by student or assigned by context? | Product decision required; justify in the report |
